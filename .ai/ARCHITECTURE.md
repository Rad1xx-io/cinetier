# Архитектура — неочевидные факты

## Обычный тир-лист
Один список на пользователя на ВСЕ категории (Films/Anime/Games/
YouTube/...) сразу, не отдельный список на категорию. Фильтр категории
в тулбаре ("Films ▾") — это фильтр ОТОБРАЖЕНИЯ, а не переключение между
разными списками. Любое массовое/деструктивное действие на этой
странице обязано явно решить, относится ли оно ко всему списку или
только к активному фильтру, и явно сказать это в тексте подтверждения.

## Кастомные доски
Отдельная модель: один пользователь — много досок (custom_tier_lists),
каждая своя. Архитектурно не связана с обычным тир-листом — это не
"ещё одна категория", а отдельный раздел.

## Публикация в ленту (обе модели постов)
Оба типа поста замораживают СТРУКТУРУ на момент публикации, но НЕ
каталожные данные — те всегда резолвятся живьём.
- Кастомные доски: custom_list_publications (013) — какая карточка в
  каком тире, в каком порядке, с какой подписью; картинки резолвятся
  через RLS/is_blocked()/hidden_at.
- Обычные тир-листы: ranked_title_publications (014) — какой
  tmdbId/mediaType в каком тире и в каком порядке; название/постер/дата
  выхода резолвятся живьём из ranked_titles, гейт видимости — is_public
  профиля (миграция 004), отдельного переключателя для этого не
  заводили.
Обе таблицы — БЕЗ UPDATE-политики (самопроверка в конце каждой
миграции): "заморожено" — свойство базы, а не обещание кода. Это две
РАЗНЫЕ таблицы, не общая абстракция — формы снепшота разные, объединять
не стали (см. .ai/DECISIONS.md, 2026-08-27). Пост без строки в
соответствующей publications-таблице — старый, опубликован до миграции,
продолжает жить по live-логике до пересоздания (Delete Post + Publish).

## ranked_titles живёт вне миграций
Таблица `ranked_titles`/`ranked_channels` определена в
supabase/schema.sql, а не в supabase/migrations/ — это самый первый,
"ручной" бутстрап схемы, применённый ДО того, как начали вести
нумерованные миграции. Любая новая миграция или тестовая проверка,
которая на неё ссылается (как 014), должна помнить, что
`supabase/testing/00_platform.sql` тоже не создаёт эту таблицу
автоматически — её пришлось добавить туда отдельным stand-in вместе с
RLS-политикой is_public-гейта из миграции 004 (которая тоже не входит в
набор миграций, что применяет supabase/testing/run.sh).

getAuthorTitles() в lib/supabase/feed.ts берёт до 40 тайтлов автора и
теперь сортирует по `id` перед этим капом (раньше не сортировала). Кап
без сортировки был безобиден для live-превью, но с приходом
ranked_title_publications (014) отсутствие тайтла в этой выборке стало
читаться как "автор его убрал" — при недетерминированном порядке это
могло быть случайностью БД, а не действием автора.

## Storage
upload_grants.image_path уникален — путь выдаётся ровно один раз за
всё время жизни проекта, attach_upload() тратит грант на одну
конкретную строку (тир или карточку). Это то, что делает безопасным
"удалить файл, если на путь никто больше не ссылается" без отдельного
счётчика ссылок — если это когда-то перестанет быть так (например,
появится дублирование карточек), removeUnreferencedFiles() сломается
молча.

## Права записи
Claude Code пишет в Supabase под JWT пользователя, без сервис-ключа —
поэтому не может сам применять миграции или писать в production
напрямую. Это всегда ручное действие Дениса через SQL Editor.

## CI
.github/workflows/ci.yml — pull_request-триггер срабатывает на любую
целевую ветку (не только main), это нарочно, чтобы stacked PR тоже
получали проверки.

## Overflow-меню тулбаров
components/ui/overflow-menu.tsx — один общий компонент для "···" на
странице обычного тир-листа и на кастомной доске. Панель позиционируется
через `position: fixed` и координаты, измеренные от `getBoundingClientRect()`
триггера в момент открытия, а не через CSS `right-0`/`absolute` внутри
обёртки триггера — простой `right-0` ломается, как только тулбар
переносится на вторую строку (flex-wrap), потому что тогда триггер стоит
у левого края строки, а не у правого края экрана. z-40, тот же уровень,
что у sticky-хедеров и категорийного дропдауна тир-листа — z-30 когда-то
уже совпал с z-30 фильтр-бара и проиграл ему по порядку в DOM.

## PostHog: посевом в snippet — нет, посевом в window — тоже нет
Интеграция — `posthog-js` как ES-модуль (`import posthog from "posthog-js"`
в app/providers/PostHogProvider.tsx), а не HTML-сниппет. Это значит
`window.posthog` НИКОГДА не появляется — если понадобится перехватить
`.capture()` из e2e/консоли браузера, ловить нужно по сети (запросы на
`NEXT_PUBLIC_POSTHOG_HOST`, например `/flags`), а не через
`window.posthog`. `capture_pageview: "history_change"` +
`opt_out_capturing_by_default` на dev — так что в `next dev` события в
PostHog реально не долетают (это осознанно, "Development noise stays
out of the project's numbers"), в `next build && next start` долетают,
если заданы `NEXT_PUBLIC_POSTHOG_KEY`/`HOST`.

`lib/analytics/tracker.ts` — единая точка выхода (`trackEvent`) для всех
провайдеров; `lib/analytics/posthog-provider.ts` регистрирует PostHog как
один из провайдеров и сам не содержит логики "что и когда трекать" — это
всегда типизированные обёртки в `lib/analytics/events.ts`, вызываемые из
компонентов/lib-слоя напрямую, а не через какой-то отдельный aggregator.

## Отчёты и скриншоты
Финальный отчёт по каждой завершённой задаче пишется в
`.ai/reports/latest.md` (перезаписывается каждый раз, не копится) и
коммитится вместе с остальной работой — Денис читает его напрямую с
диска через мост к своему компьютеру, не из чата. Скриншоты для
визуальной проверки — в `.ai/reports/shots/`, тоже очищаются перед
каждым новым набором, названы по смыслу. Подробности в
`.ai/reports/README.md`.
